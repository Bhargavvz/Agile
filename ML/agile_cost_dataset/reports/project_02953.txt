1. Project Overview

This project addresses a critical challenge in the IoT domain. Connected-home device ecosystems are fragmented, preventing seamless inter-device automation for consumers. To respond to this challenge, the project team has set a clear business goal: Build an interoperable smart-home hub that allows seamless automation across device brands.

The primary target users for this system are homeowners, facility managers and field technicians. The solution is designed to streamline their workflows and deliver measurable value within 2 months of development.

2. Agile Framework

The project follows the Scrum framework, which organises work into fixed-length iterations known as sprints. Each sprint lasts 2 weeks, giving the team a steady cadence for planning, development, review, and retrospective activities.

Scrum roles have been clearly defined. A Product Owner is responsible for maintaining and prioritising the product backlog in collaboration with stakeholders. A Scrum Master facilitates ceremonies, removes impediments, and coaches the team on Agile practices. The Development Team of 3 members is cross-functional, comprising front-end and back-end developers, QA engineers, and — where needed — DevOps specialists.

The incremental delivery approach ensures that a potentially shippable product increment is available at the end of every sprint. This allows stakeholders to provide feedback early and often, reducing the cost of late-stage requirement changes.

3. Product Backlog & User Stories

The product backlog contains 12 user stories that have been identified, estimated, and prioritised during initial backlog grooming sessions. Story-point estimates follow the Fibonacci-like scale (1, 2, 3, 5, 8, 13) and reflect the relative complexity, effort, and uncertainty of each item. The average story-point value across the backlog is approximately 2.5.

  - As a technician, I want to access historical sensor data so that trends and patterns are easy to analyse. [1 story points]
  - As a manager, I want to schedule predictive maintenance tasks so that equipment reliability improves over time. [3 story points]
  - As a technician, I want to view real-time sensor readings so that I can assess equipment status from anywhere. [8 story points]
  - As a technician, I want to update device firmware remotely so that field visits for routine updates are eliminated. [1 story points]
  - As a technician, I want to run remote diagnostics so that root-cause analysis does not require a site visit. [13 story points]
  - As a admin, I want to integrate with ERP systems so that operational and business data are synchronised. [3 story points]
  - As a admin, I want to manage certificates for device TLS so that communication channels are encrypted. [8 story points]
  - As a admin, I want to define multi-tenant device access so that shared infrastructure is logically separated. [3 story points]
  - As a technician, I want to view wiring and schematic diagrams so that maintenance is guided by accurate documentation. [8 story points]
  - As a manager, I want to compare performance across locations so that best practices are identified and replicated. [5 story points]
  - As a manager, I want to view fleet-wide device health dashboards so that I have visibility across all deployed assets. [1 story points]
  - As a admin, I want to manage device grouping and tagging so that assets are organised logically. [13 story points]

4. Sprint Planning & Velocity

The project spans 2 months and is divided into 4 sprints of 2 weeks each. Based on the team's estimated capacity and historical data from similar projects, the anticipated velocity is approximately 6.0 story points per sprint.

During sprint planning, the Product Owner presents the highest-priority items from the backlog, and the Development Team selects stories whose combined estimates fit within the sprint velocity. Any incomplete stories are carried over to the next sprint after a brief retrospective discussion to identify the root cause.

Sprint reviews provide stakeholders with a live demonstration of new features. Sprint retrospectives capture lessons learned and actionable improvements, fostering continuous process enhancement.

5. System Architecture & Modules

The architecture favours simplicity and rapid delivery. A monolithic application structure keeps the codebase manageable for a small team while still supporting the planned feature set.

The following core modules have been identified:

  - User Authentication: Simple email/password login with session management
  - Dashboard: Basic summary view with key metrics
  - CRUD Module: Standard create, read, update, delete operations for core entities
  - Reporting: Pre-defined report templates with CSV export

6. Technology Stack

Frontend : Vue.js
Backend  : Flask
Database : MySQL
Cloud    : Railway

The stack is intentionally kept straightforward — no AI, ML, or real-time components are required. This positions the technical difficulty at 'Basic', keeping the cost-per-hour and effort multipliers at their baseline values.

7. Risk & Requirement Volatility

The overall risk level for this project is assessed as 'Low', and requirement volatility is rated 'Low'. Requirements have been well-defined upfront, and only minor refinements are anticipated during later sprints. 

Key risks identified:
  - Minor scope adjustments expected during later sprints.
  - Potential minor delays if key team members take planned leave.

Mitigation strategies adopted by the team:
  - Schedule knowledge-transfer sessions to reduce bus-factor risk.
  - Automate regression tests to catch breakages from dependency updates.
