1. Project Overview

This project addresses a critical challenge in the SaaS domain. SaaS vendors struggle to monitor real-time application health and proactively prevent downtime for their customers. To respond to this challenge, the project team has set a clear business goal: Unify team collaboration through an integrated workspace combining chat, tasks, and docs.

The primary target users for this system are customer success managers and development teams. The solution is designed to streamline their workflows and deliver measurable value within 2 months of development.

2. Agile Framework

The project follows the Scrum framework, which organises work into fixed-length iterations known as sprints. Each sprint lasts 2 weeks, giving the team a steady cadence for planning, development, review, and retrospective activities.

Scrum roles have been clearly defined. A Product Owner is responsible for maintaining and prioritising the product backlog in collaboration with stakeholders. A Scrum Master facilitates ceremonies, removes impediments, and coaches the team on Agile practices. The Development Team of 5 members is cross-functional, comprising front-end and back-end developers, QA engineers, and — where needed — DevOps specialists.

The incremental delivery approach ensures that a potentially shippable product increment is available at the end of every sprint. This allows stakeholders to provide feedback early and often, reducing the cost of late-stage requirement changes.

3. Product Backlog & User Stories

The product backlog contains 13 user stories that have been identified, estimated, and prioritised during initial backlog grooming sessions. Story-point estimates follow the Fibonacci-like scale (1, 2, 3, 5, 8, 13) and reflect the relative complexity, effort, and uncertainty of each item. The average story-point value across the backlog is approximately 3.9.

  - As a admin, I want to manage role-based permissions so that data access follows the principle of least privilege. [13 story points]
  - As a user, I want to share a view-only link externally so that stakeholders can review without an account. [3 story points]
  - As a user, I want to search across all projects so that I can find information quickly. [3 story points]
  - As a user, I want to receive in-app notifications so that I stay up to date without checking email. [1 story points]
  - As a user, I want to use keyboard shortcuts so that power users can navigate faster. [2 story points]
  - As a admin, I want to set up multi-region data residency so that data sovereignty requirements are met. [2 story points]
  - As a admin, I want to offer a white-label option so that partners can rebrand the product. [8 story points]
  - As a user, I want to create and share templates so that common tasks are standardised across the team. [5 story points]
  - As a user, I want to sign up and start a free trial so that I can evaluate the product risk-free. [1 story points]
  - As a user, I want to customise my dashboard layout so that I see the metrics most relevant to my role. [1 story points]
  - As a admin, I want to manage API rate limits per tenant so that fair usage is enforced across clients. [2 story points]
  - As a user, I want to integrate with third-party apps via API so that my workflow remains uninterrupted. [8 story points]
  - As a user, I want to bookmark frequently used resources so that I access key items with one click. [3 story points]

4. Sprint Planning & Velocity

The project spans 2 months and is divided into 4 sprints of 2 weeks each. Based on the team's estimated capacity and historical data from similar projects, the anticipated velocity is approximately 15.6 story points per sprint.

During sprint planning, the Product Owner presents the highest-priority items from the backlog, and the Development Team selects stories whose combined estimates fit within the sprint velocity. Any incomplete stories are carried over to the next sprint after a brief retrospective discussion to identify the root cause.

Sprint reviews provide stakeholders with a live demonstration of new features. Sprint retrospectives capture lessons learned and actionable improvements, fostering continuous process enhancement.

5. System Architecture & Modules

The architecture favours simplicity and rapid delivery. A monolithic application structure keeps the codebase manageable for a small team while still supporting the planned feature set.

The following core modules have been identified:

  - User Authentication: Simple email/password login with session management
  - Dashboard: Basic summary view with key metrics
  - CRUD Module: Standard create, read, update, delete operations for core entities
  - Reporting: Pre-defined report templates with CSV export

6. Technology Stack

Frontend : HTML/CSS/JS
Backend  : Flask
Database : MySQL
Cloud    : Heroku

The stack is intentionally kept straightforward — no AI, ML, or real-time components are required. This positions the technical difficulty at 'Basic', keeping the cost-per-hour and effort multipliers at their baseline values.

7. Risk & Requirement Volatility

The overall risk level for this project is assessed as 'Low', and requirement volatility is rated 'Medium'. Stakeholder priorities are expected to shift during the course of the project, which may lead to backlog re-prioritisation and scope adjustments across sprints. 

Key risks identified:
  - Minor scope adjustments expected during later sprints.
  - Potential minor delays if key team members take planned leave.

Mitigation strategies adopted by the team:
  - Establish a formal change-request process to manage scope creep.
  - Implement feature flags to isolate risky changes behind toggles.
  - Conduct bi-weekly stakeholder review sessions to catch requirement drift.
  - Maintain a spike backlog for research tasks to de-risk unknowns early.
