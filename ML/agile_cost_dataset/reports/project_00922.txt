1. Project Overview

This project addresses a critical challenge in the EdTech domain. Current learning management systems do not adapt content difficulty to individual learner progress. To respond to this challenge, the project team has set a clear business goal: Launch an adaptive e-learning platform that personalises content to each student's proficiency level.

The primary target users for this system are content creators, teachers and academic administrators. The solution is designed to streamline their workflows and deliver measurable value within 4 months of development.

2. Agile Framework

The project follows the Scrum framework, which organises work into fixed-length iterations known as sprints. Each sprint lasts 2 weeks, giving the team a steady cadence for planning, development, review, and retrospective activities.

Scrum roles have been clearly defined. A Product Owner is responsible for maintaining and prioritising the product backlog in collaboration with stakeholders. A Scrum Master facilitates ceremonies, removes impediments, and coaches the team on Agile practices. The Development Team of 4 members is cross-functional, comprising front-end and back-end developers, QA engineers, and — where needed — DevOps specialists.

The incremental delivery approach ensures that a potentially shippable product increment is available at the end of every sprint. This allows stakeholders to provide feedback early and often, reducing the cost of late-stage requirement changes.

3. Product Backlog & User Stories

The product backlog contains 12 user stories that have been identified, estimated, and prioritised during initial backlog grooming sessions. Story-point estimates follow the Fibonacci-like scale (1, 2, 3, 5, 8, 13) and reflect the relative complexity, effort, and uncertainty of each item. The average story-point value across the backlog is approximately 2.7.

  - As a teacher, I want to create and publish course content so that my students have access to up-to-date materials. [13 story points]
  - As a admin, I want to manage user enrolments so that course rosters are accurate and up to date. [1 story points]
  - As a student, I want to view my progress across all courses so that I can manage my learning path effectively. [13 story points]
  - As a admin, I want to issue digital certificates so that graduates have verifiable proof of completion. [13 story points]
  - As a teacher, I want to create reusable question banks so that quiz creation becomes more efficient. [3 story points]
  - As a teacher, I want to track student attendance so that I can identify disengaged learners early. [1 story points]
  - As a student, I want to access course materials offline so that I can study without an internet connection. [1 story points]
  - As a teacher, I want to set up adaptive quizzes so that questions adjust to each student's ability level. [3 story points]
  - As a teacher, I want to host office hours via video call so that students get personalised help when needed. [1 story points]
  - As a student, I want to receive deadline reminders so that I never miss an assignment due date. [2 story points]
  - As a admin, I want to handle financial-aid applications so that eligible students receive support promptly. [5 story points]
  - As a admin, I want to manage campus-wide announcements so that important updates reach all stakeholders. [5 story points]

4. Sprint Planning & Velocity

The project spans 4 months and is divided into 8 sprints of 2 weeks each. Based on the team's estimated capacity and historical data from similar projects, the anticipated velocity is approximately 8.6 story points per sprint.

During sprint planning, the Product Owner presents the highest-priority items from the backlog, and the Development Team selects stories whose combined estimates fit within the sprint velocity. Any incomplete stories are carried over to the next sprint after a brief retrospective discussion to identify the root cause.

Sprint reviews provide stakeholders with a live demonstration of new features. Sprint retrospectives capture lessons learned and actionable improvements, fostering continuous process enhancement.

5. System Architecture & Modules

The architecture favours simplicity and rapid delivery. A monolithic application structure keeps the codebase manageable for a small team while still supporting the planned feature set.

The following core modules have been identified:

  - User Authentication: Simple email/password login with session management
  - Dashboard: Basic summary view with key metrics
  - CRUD Module: Standard create, read, update, delete operations for core entities
  - Reporting: Pre-defined report templates with CSV export

6. Technology Stack

Frontend : Bootstrap + jQuery
Backend  : Flask
Database : PostgreSQL
Cloud    : Render

The stack is intentionally kept straightforward — no AI, ML, or real-time components are required. This positions the technical difficulty at 'Basic', keeping the cost-per-hour and effort multipliers at their baseline values.

7. Risk & Requirement Volatility

The overall risk level for this project is assessed as 'Low', and requirement volatility is rated 'Low'. Requirements have been well-defined upfront, and only minor refinements are anticipated during later sprints. 

Key risks identified:
  - Minor scope adjustments expected during later sprints.
  - Potential minor delays if key team members take planned leave.

Mitigation strategies adopted by the team:
  - Automate regression tests to catch breakages from dependency updates.
  - Schedule knowledge-transfer sessions to reduce bus-factor risk.
  - Use contract testing for third-party API integrations.
  - Conduct bi-weekly stakeholder review sessions to catch requirement drift.
