1. Project Overview

This project addresses a critical challenge in the FinTech domain. Fraud detection in real-time payment streams remains inadequate, exposing financial institutions to rising losses. To respond to this challenge, the project team has set a clear business goal: Offer a unified personal-finance dashboard aggregating data from multiple banking institutions.

The primary target users for this system are compliance analysts, banking customers and financial advisors. The solution is designed to streamline their workflows and deliver measurable value within 4 months of development.

2. Agile Framework

The project follows the Scrum framework, which organises work into fixed-length iterations known as sprints. Each sprint lasts 2 weeks, giving the team a steady cadence for planning, development, review, and retrospective activities.

Scrum roles have been clearly defined. A Product Owner is responsible for maintaining and prioritising the product backlog in collaboration with stakeholders. A Scrum Master facilitates ceremonies, removes impediments, and coaches the team on Agile practices. The Development Team of 4 members is cross-functional, comprising front-end and back-end developers, QA engineers, and — where needed — DevOps specialists.

The incremental delivery approach ensures that a potentially shippable product increment is available at the end of every sprint. This allows stakeholders to provide feedback early and often, reducing the cost of late-stage requirement changes.

3. Product Backlog & User Stories

The product backlog contains 10 user stories that have been identified, estimated, and prioritised during initial backlog grooming sessions. Story-point estimates follow the Fibonacci-like scale (1, 2, 3, 5, 8, 13) and reflect the relative complexity, effort, and uncertainty of each item. The average story-point value across the backlog is approximately 3.0.

  - As a analyst, I want to view transaction risk scores so that I can investigate suspicious activity efficiently. [1 story points]
  - As a customer, I want to export tax-ready financial statements so that I can file taxes without manual calculation. [8 story points]
  - As a customer, I want to link external bank accounts so that all my finances are visible in one place. [5 story points]
  - As a analyst, I want to backtest fraud-detection models so that rule effectiveness is validated before deployment. [1 story points]
  - As a customer, I want to set up recurring bill payments so that my bills are paid automatically. [3 story points]
  - As a customer, I want to set savings goals with auto-transfers so that I build savings effortlessly. [3 story points]
  - As a admin, I want to configure multi-currency support so that international users can transact seamlessly. [5 story points]
  - As a customer, I want to enable biometric login so that my account access is both fast and secure. [5 story points]
  - As a customer, I want to initiate a chargeback request so that disputed transactions are resolved fairly. [8 story points]
  - As a analyst, I want to run anti-money-laundering checks so that the platform complies with financial regulations. [13 story points]

4. Sprint Planning & Velocity

The project spans 4 months and is divided into 8 sprints of 2 weeks each. Based on the team's estimated capacity and historical data from similar projects, the anticipated velocity is approximately 9.6 story points per sprint.

During sprint planning, the Product Owner presents the highest-priority items from the backlog, and the Development Team selects stories whose combined estimates fit within the sprint velocity. Any incomplete stories are carried over to the next sprint after a brief retrospective discussion to identify the root cause.

Sprint reviews provide stakeholders with a live demonstration of new features. Sprint retrospectives capture lessons learned and actionable improvements, fostering continuous process enhancement.

5. System Architecture & Modules

The architecture favours simplicity and rapid delivery. A monolithic application structure keeps the codebase manageable for a small team while still supporting the planned feature set.

The following core modules have been identified:

  - User Authentication: Simple email/password login with session management
  - Dashboard: Basic summary view with key metrics
  - CRUD Module: Standard create, read, update, delete operations for core entities
  - Reporting: Pre-defined report templates with CSV export

6. Technology Stack

Frontend : HTML/CSS/JS
Backend  : Flask
Database : PostgreSQL
Cloud    : Railway

The stack is intentionally kept straightforward — no AI, ML, or real-time components are required. This positions the technical difficulty at 'Basic', keeping the cost-per-hour and effort multipliers at their baseline values.

7. Risk & Requirement Volatility

The overall risk level for this project is assessed as 'Low', and requirement volatility is rated 'Low'. Requirements have been well-defined upfront, and only minor refinements are anticipated during later sprints. 

Key risks identified:
  - Minor scope adjustments expected during later sprints.
  - Potential minor delays if key team members take planned leave.

Mitigation strategies adopted by the team:
  - Automate regression tests to catch breakages from dependency updates.
  - Implement feature flags to isolate risky changes behind toggles.
  - Maintain a spike backlog for research tasks to de-risk unknowns early.
  - Keep a 15% time buffer in each sprint for unplanned work.
